# 容量规划会话交接

> 状态：阶段 D 已实现；RAG 与具体教室推荐保留为后续阶段。
>
> 项目：知讲 TalkWise（Spring Boot 3.1.5 + Vue 3 + MySQL + LangChain4j 单 Agent）

## 1. 本次讨论目标

为讲座创建前提供容量建议。该建议不能只看历史报名统计，还要综合语义因素，避免把“统计平均值”误当成真实需求。

目标场景：教师在 Agent 对话中询问类似“我准备办一场《XX》讲座，建议设置多少容量？”时，Agent 根据历史数据和语义判断，给出建议容量、依据和不确定性说明。

本轮已按确认方案实现建议容量工具；本轮不实现 RAG、具体教室推荐、自动创建讲座或修改 lecture.capacity。

## 2. 已明确的容量判断模型

容量评估采用“统计基准 × 语义修正”的混合模型：

```text
建议容量 = base × k(内容热度) × k(讲师声望) × k(校本契合度)
```

其中：

- `base`：历史报名/签到数据推得的统计基准。历史数据不足时使用配置的默认容量。
- `k(内容热度)`：讲座主题在当前社会、行业和学生群体中的关注度。
- `k(讲师声望)`：讲师的职称、简介、历史讲座表现、校内认可度等。
- `k(校本契合度)`：**本次新增的重要维度**。讲座主题与学校主流方向、办学定位、优势学科之间的匹配程度。

示例：学校以工科、软件工程、人工智能等方向为主时，工科类讲座通常具有更高的潜在受众，校本契合度应上调；与学校主流方向关联较弱的主题则不应因为“社会热点”而被过度放大。

## 3. 语义判断与规则计算的边界

保持既定原则：

- LLM 只输出定性判断，不直接决定容量数字。
- 后端规则层根据高/中/低等级映射为配置化系数、做边界裁剪和取整。
- 最终输出要包含建议理由、数据不足提示和置信边界。

建议的结构化语义输出：

```json
{
  "contentHeat": "HIGH",
  "speakerReputation": "MEDIUM",
  "schoolFit": "HIGH",
  "reason": "主题与学校重点学科高度相关，且面向学生群体覆盖面较广。"
}
```

建议的初始标定值（仅为可调默认值，非固定真理）：

| 维度 | 高 | 中 | 低 |
| --- | ---: | ---: | ---: |
| 内容热度 | 1.30 | 1.00 | 0.80 |
| 讲师声望 | 1.20 | 1.00 | 0.85 |
| 校本契合度 | 1.30 | 1.00 | 0.80 |

还需配置：

- `default-capacity`：冷启动时的默认容量
- `min-capacity` / `max-capacity`：建议容量边界
- `round-to`：容量取整粒度，例如 5 或 10
- 历史样本最小阈值：达到阈值才采用统计基准

## 4. 学校画像与 RAG 的关系

用户提出：后续会提供学校介绍，并放入 RAG，作为容量判断标准之一。

### 4.1 当前判断

学校介绍通常只有一两页，直接作为“学校画像”全文注入容量评估 prompt 即可。对这类短文本，RAG 并非工程必需；分块和召回反而可能遗漏重要的学科定位信息。

因此，容量评估应先抽象为“获取学校画像”的数据来源，而不是把 RAG 写死在容量计算里：

```text
当前：学校画像配置/数据库记录 -> 全文注入 LLM prompt
后续：RAG 检索相关学校画像片段 -> 注入同一个 LLM prompt
```

这样未来引入 RAG 时，容量计算主流程不需要重写。

### 4.2 RAG 的推荐定位

RAG 更适合作为独立能力建设：

```text
管理员上传学校介绍、培养方案、制度文件等
  -> 文档分块、向量化、持久化
  -> 师生通过 Agent 进行知识库问答
  -> 容量评估按讲座主题检索学校相关片段作为“校本契合度”上下文
```

这样 RAG 是项目可见的独立技术能力，而不是隐藏在容量计算内部的一段实现。

### 4.3 关键技术约束

当前对话模型是 DeepSeek（OpenAI 兼容 chat/function calling）。DeepSeek API 不提供可直接使用的 embedding 接口，因此 RAG 需要额外选择 embedding 方案，例如：

- 云端：硅基流动 BGE-M3、阿里云通义 embedding 等
- 本地：Ollama + `nomic-embed-text` 或 BGE 系列模型

RAG 的 embedding 供应商、向量存储和文档管理应作为独立阶段选型，不应混入本轮容量规划的最小实现。

## 5. 已核对的数据事实与缺口

已检查当前实体：

- `Location` 没有 `capacity` 字段，只有名称、经纬度、类型、地址等。因此当前无法基于真实教室上限做“推荐教室”。
- `User` 没有 `intro`、`title`、`bio` 等讲师简介字段。教师个人中心的简介编辑此前处于未开放状态，因此“讲师社会知名度”目前没有稳定的校内数据来源。

这带来两个数据建设点：

1. 若要可信地评估讲师声望，应新增教师简介/职称等可维护字段，且不能只靠模型猜测。
2. 若要输出“推荐教室”，应给 `location` 增加 `capacity` 并由管理员维护；否则本轮只输出建议容量，不承诺教室推荐。

## 6. 建议的实施范围（待用户确认后才可开始）

### 纳入本轮容量规划

1. 统计基准计算：历史报名、取消、签到等数据形成基础容量。
2. 三个语义维度：内容热度、讲师声望、校本契合度。
3. LLM 输出定性等级，后端做规则融合、裁剪和取整。
4. `estimateCapacity(...)` Agent 工具，仅对教师和管理员开放。
5. 评估结果返回建议容量、影响因素、数据样本量和不确定性说明。
6. 学校画像数据源预留为可替换接口，当前不依赖 RAG。

### 不纳入本轮

1. 完整 RAG 知识库、文件上传、文档解析、向量化与检索管理。
2. 对话式创建讲座。
3. 自动替教师创建讲座或自动修改容量。
4. 在缺少 `location.capacity` 前提下的推荐教室。
5. 将 LLM 输出直接当作容量数字写库。

## 7. 推荐的数据设计方向

### 学校画像

推荐使用数据库单行配置/资料表，而不是仅写入 `application.yml`：

- 管理员可以维护学校办学定位、优势学科、重点方向和学生群体特征。
- 后续 RAG 可将该数据作为首份知识库文档。
- 学校画像为空时，校本契合度不参与计算，系数固定为 `1.0`，结果中必须明示未使用该维度。

### 讲师资料

建议为教师增加可维护的简介/职称信息。容量评估需要的是可解释、可追溯的输入，不能让 LLM 在没有资料时臆断讲师影响力。

### 场地容量

仅当用户确认需要“推荐教室”时新增 `location.capacity`。否则容量建议可以独立完成，不需要为了未来能力提前改动场地表。

## 8. 设计取舍

用户指出“学校主流方向只是一个判断标准”，未来可能加入时段、同期竞争讲座、季节、社会事件等维度。

建议当前不要做通用的“动态指标引擎”。先明确实现三个语义维度并把系数配置化；等第四个稳定维度确实出现，再把维度抽象为可扩展清单。原因是当前过度抽象会增加配置和调试成本，且没有真实需求验证。

## 11. 当前项目上下文补充

- 后端：Spring Boot 3.1.5、MyBatis-Plus、Sa-Token、MySQL。
- Agent：LangChain4j 0.35.0，DeepSeek `deepseek-v4-flash`，单 Agent + 工具路由。
- 现有工具路由域：`lecture`、`registration`、`statistics`、`content`、`analysis`、`general`。
- 容量估算工具可先放在 `analysis` 域，教师和管理员可用。
- Agent 原则：模型负责理解与定性判断；代码负责权限、数据查询、数值规则、边界和写操作守门。
- 现有历史数据可能包含报名与签到数据；签到时间字段已在近期功能中设计为 `registration.checkin_time`，用户仍需执行相应数据库升级 SQL。

# Tool Routing：工具多了怎么让 Agent 选得更准

> 本文档记录知讲 TalkWise 的工具路由设计：方法论参照业界分层 Tool Routing 方案（面试高频题），
> 并逐条对照本项目实现，标注当前方案与演进路径。

## 1. 问题：工具多了为什么调不准

把全部工具 Schema 塞进 Prompt 会同时引发四类问题：

| 问题 | 表现 |
|---|---|
| Token 占用 | 工具定义与系统提示、历史、证据抢上下文；输入成本上升 |
| 选择混淆 | 相似工具（描述高度重叠）之间误选——根因是工具边界没说清 |
| 权限暴露 | 无权调用的能力出现在模型视野里，扩大误调用与提示词注入的攻击面 |
| 延迟压力 | 更长的输入 + 更大的候选判断空间；目标是端到端时延，而非单点更快 |

## 2. 概念边界：Tool Routing ≠ Multi-Agent Routing

- **Tool Routing**：决定「当前这个 Agent 此刻能看到、能选择哪些工具」——路由对象是**工具候选集**
- **Multi-Agent Routing**：决定「任务交给哪个 Agent」——路由对象是**执行者/任务归属**

两者可分层配合（先选 Agent 缩小业务边界，Agent 内部再选工具缩小能力边界），但不能混淆；
也不能为了规避工具过多而无原则拆几十个 Agent（只是把工具目录变成 Agent 目录）。

## 3. 分层链路（业界方案）与本项目实现对照

| 步骤 | 业界方案 | 本项目实现 | 状态 |
|---|---|---|---|
| ① 工具注册表 | 工具卡片：命名空间、能做什么、何时用/何时不用、Schema、标签、权限风险、状态 | `@AgentTool`：`name` / `description`（四段式）/ `domain` 域标签 / `roles` 角色 / `type` 读写分级；注册表启动扫描 | ✅ |
| ② 确定性过滤 | **先鉴权再做相关性召回**：静态 Allowlist + 动态（角色/租户/任务状态） | `ToolRouter` 身份过滤：按当前用户角色裁剪（学生/游客看不到管理类工具） | ✅ |
| ③ 粗分类缩域 | 规则或轻量分类模型；高召回偏置（多意图保留多域）；不确定则跳过 | 关键词命中工具域（statistics/analysis/content/registration/lecture）；**命中多域全保留**；未命中不裁剪 | ✅（规则版） |
| ④ 候选域内检索 | 关键词/BM25/Embedding/混合检索 Top-K | 未实现（当前 7 个工具，粗分类后候选已很小） | ⏳ 工具 15+ 时升级 |
| ⑤ 动态绑定精选 | 只把候选工具完整 Schema 绑定给模型，由模型决定是否调用/选哪个/填参数 | 每轮对话只下发路由后的工具 Schema；模型在候选集内自主决策 | ✅ |
| 常驻策略 | 高频低风险工具常驻，长尾按需加载 | `lecture` 基础域 + `general` 域常驻（找讲座是全流程入口，报名/推荐都依赖它拿 ID） | ✅ |
| 执行层安全 | 隐藏 ≠ 鉴权：执行时按参数与资源归属再校验 | 工具内二次校验（角色 + 资源归属，如教师仅限本人讲座）+ **候选集外调用运行时拒绝** | ✅ |

## 4. 本项目的执行细节

### 请求链路

```
用户消息
  → ToolRouter.route(all, message, roles)
      ① 身份过滤：tool.roles 为空=公开；非空要求角色交集
      ② 意图过滤：消息关键词命中域 → 候选 = 命中域 ∪ {lecture, general}
      ③ 兜底：未命中任何域 → 不裁剪；裁剪后为空 → 退回全量
  → 候选工具 Schema 下发模型（本轮对话固定，多轮循环复用）
  → 模型输出工具调用
  → dispatch 校验：调用必须在候选集内（否则运行时拒绝并回填提示）
  → 执行（WRITE 记审计日志）→ 结果回填 → 模型组织回答
```

### 可观测

- 路由日志：`[Agent路由] 命中域 [analysis]，工具 7 → 2 个`
- 拒绝日志：`[Agent审计] 拒绝候选集外工具调用: xxx`
- 工具轨迹随响应返回前端展示（`🔧 查询讲座` 等标签）

## 5. 演进路径（工具规模决定复杂度）

| 工具规模 | 方案 |
|---|---|
| < 15（当前 7 个） | 关键词规则粗分类 + 身份过滤（本实现） |
| 15 ~ 50 | 引入 embedding 检索召回 Top-K（工具卡片向量化，名称/标签/场景/排除条件均入索引），可混合 BM25 |
| > 50 | 检索 + reranker；高召回偏置；按 Skill/工作流进一步缩小命名空间；高风险动作进入确定性规则或人工审批 |

**核心原则**：检索追求「别漏掉正确工具」（高召回），不是「排第一就直接执行」——
相似度只表示语义接近，不代表有权限、参数满足、任务可完成。

## 6. 评测指标（要拆开链路看）

| 层 | 指标 |
|---|---|
| 召回层 | Recall@K（正确工具是否进 Top-K，多工具任务看完整性）、候选集大小、Schema Token |
| 精选层 | 最终工具选择准确率、相似工具误选率、该答不调（拒选准确率）、该调不调（漏调率）、参数合法率 |
| 业务层 | 任务成功率、执行失败率、端到端延迟、成本、澄清率、人工接管率 |
| 安全 | 未授权工具暴露率、越权调用拦截、高风险操作审批覆盖率 |

**评测集**：除简单题外必须包含——相似工具 Hard Negative、多意图请求、无需工具的请求、缺参数请求、无权限请求、历史 Badcase。上线保留每层候选/分数/过滤原因/最终调用 Trace，出错才能定位是召回漏了还是模型选错了。

## 7. 兜底策略对照

| 场景 | 业界建议 | 本项目 |
|---|---|---|
| 无候选/置信度低 | 改写查询扩大召回，或让用户澄清 | 未命中域不裁剪（天然高召回）；澄清依赖提示词规则④ |
| 候选外工具名 | **运行时必须拒绝**，不做「将错就错」映射 | ✅ dispatch 候选集校验 |
| 首选不可用 | 备用工具/降级人工 | 工具执行失败信息回填，模型自主换策略（引擎循环） |
| 高风险动作低置信 | 进确定性规则或人工审批 | 写操作直接执行（产品决策：明确指令即授权），以审计 + Service 校验兜底 |

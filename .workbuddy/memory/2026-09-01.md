## Agent 化改造分析（只读检查，未改代码）
- 项目：高校讲座管理系统（Spring Boot 3 + Vue3，MySQL，Sa-Token，WebSocket）
- 现状 AI：AiAssistantController/AiAssistantServiceImpl 已接通义千问（API Key 硬编码在代码中，安全隐患），采用硬编码关键词意图识别 + 拼 10 场讲座进 prompt，前端 StudentAi.vue
- 库中空置 AI 字段：lecture.seo_title/keywords/recommend_reason、evaluation.sentiment_score/improvement_suggestion、recommendation_log 表、interaction 问答表
- 结论分三档：值得 Agent 化 = AI 助手多工具化、个性化推荐、自然语言查数据、自动答疑；LLM 功能点即可 = 评价情感分析、SEO 文案生成、发布审核辅助；不建议 = 报名/签到、定时状态流转（@Scheduled 已实现）、管理 CRUD、地图通知
- 已向用户讲清 Agent 概念（LLM+工具+循环，区别于普通调用/工作流/聊天机器人），并给出 22 项功能逐项判定清单
- 判定标准沉淀：输入不确定/需多步决策/有判断空间 → Agent 化；规则明确/高可靠要求/已有成熟实现 → 保持传统代码；单步调用输出固定 → LLM 功能点
- 修订（用户提出后采纳）：容量规划（创建讲座时 AI 依据教师历史满座率/相似主题/兴趣标签匹配数推荐容量与教室，教师确认）升级为第 5 项 Agent 化功能；但运行时容量控制（满员判断/候补触发）与报名取消的业务规则仍保持确定性代码——Agent 可作为调用报名的"执行入口"（工具包装），不能替代码做业务决策
- 二次修订（用户确认）：Agent 化清单增至 6 项。新增：候补智能递补（取消事件→Agent 按 historical 签到率/user.participation_score/兴趣匹配预测到场概率→生成递补建议名单→默认教师确认、自动模式需置信度护栏）；学生报名/取消由 Agent 直接执行（工具包装：Sa-Token 本人身份透传、写操作对话内二次确认、防重复/截止时间等规则仍在 Service 层、幂等+审计日志）。最终 Agent 化 6 项：助手多工具化、个性化推荐、自然语言查数据、答疑、容量规划、候补智能递补
